# cct-catalog

CCT - DevOps summer course 2026.

A small **Django** web application exposing a **REST API**, built as coursework
for the CCT DevOps summer course. The project is a book catalogue service
(`bookcatalog`), with a full delivery pipeline: containerised with Docker,
released automatically via semantic-release, and deployed to Kubernetes with
Helm.

## Tech stack

- **Python** 3.12 (Docker image) — web app
- **Django** 6.0 — web framework
- **Django REST Framework** 3.17 — REST API layer
- **PostgreSQL** 17 — database (Docker Compose / production)
- **SQLite** — development database (`db.sqlite3`, used when `DEVELOPMENT_MODE=true`)
- **pytest** + **pytest-django** — test suite
- **Docker** / **Docker Compose** — containerisation and local stack
- **GitHub Actions** — CI/CD (tests, migration checks, release, image build)
- **semantic-release** — automated versioning and changelog from conventional commits
- **Helm** — Kubernetes deployment chart (`books-catalog-chart/`)

## The API

The `api` app exposes a book catalogue backed by the `Book` model
(`title`, `author`, `isbn`, `published_date`), organised in service/repository
layers with a dedicated view per operation:

| Method    | Path                        | Description                              |
| --------- | --------------------------- | ----------------------------------------- |
| GET       | `/api/books/`                | List all books                            |
| POST      | `/api/books/create/`         | Create a book                             |
| GET       | `/api/books/<id>/`           | Retrieve a single book (404 if not found) |
| PUT/PATCH | `/api/books/<id>/update/`    | Update a book (404 if not found)          |
| DELETE    | `/api/books/<id>/delete/`    | Delete a book (404 if not found)          |

Validation rules (`BookSerializer`):
- `title` / `author`: required, non-blank.
- `isbn`: must be exactly 13 digits (hyphens are stripped), and unique across books.

The Django admin is available at `/admin/`.

## API usage examples

All examples below assume the app is running locally at
`http://127.0.0.1:8000` (see [Running locally](#running-locally)). You can
run these with `curl`, or use [Swagger UI](#api-documentation-swagger--openapi)
to try them interactively in the browser.

### List all books

```bash
curl -X GET http://127.0.0.1:8000/api/books/
```

Response — `200 OK`:

```json
[
  {
    "id": 1,
    "title": "Clean Architecture",
    "author": "Robert C. Martin",
    "isbn": "9780134494166",
    "published_date": "2017-09-20"
  }
]
```

### Create a book

```bash
curl -X POST http://127.0.0.1:8000/api/books/create/ \
  -H "Content-Type: application/json" \
  -d '{
        "title": "Clean Architecture",
        "author": "Robert C. Martin",
        "isbn": "9780134494166",
        "published_date": "2017-09-20"
      }'
```

Response — `201 Created`, returning the created record with its generated `id`:

```json
{
  "id": 1,
  "title": "Clean Architecture",
  "author": "Robert C. Martin",
  "isbn": "9780134494166",
  "published_date": "2017-09-20"
}
```

Response — `400 Bad Request` if validation fails (e.g. a duplicate or
malformed `isbn`):

```json
{
  "isbn": ["A book with this ISBN already exists."]
}
```

### Retrieve a single book

```bash
curl -X GET http://127.0.0.1:8000/api/books/1/
```

Response — `200 OK` with the matching book, or `404 Not Found` if no book
with that `id` exists:

```json
{
  "detail": "Not found."
}
```

### Update a book

`PATCH` updates only the supplied fields; `PUT` expects the full payload.

```bash
curl -X PATCH http://127.0.0.1:8000/api/books/1/update/ \
  -H "Content-Type: application/json" \
  -d '{"title": "Clean Architecture (2nd Edition)"}'
```

Response — `200 OK` with the updated record, or `404 Not Found` if the
book does not exist.

### Delete a book

```bash
curl -X DELETE http://127.0.0.1:8000/api/books/1/delete/
```

Response — `204 No Content` on success, or `404 Not Found` if the book does
not exist.

## API documentation (Swagger / OpenAPI)

The API schema is generated automatically with `drf-spectacular`, which
introspects the Django REST Framework views, serializers and URL routes to
build an OpenAPI 3 document. No documentation is written by hand — it is
always in sync with the actual code. Three endpoints are served alongside
the app:

| Path            | Description                          |
| --------------- | ------------------------------------- |
| `/api/schema/`  | Raw OpenAPI 3 schema (YAML)           |
| `/api/docs/`    | Swagger UI                            |
| `/api/redoc/`   | Redoc UI                              |

### Accessing Swagger UI

Once the app is running (either locally or via Docker Compose, see
[Running locally](#running-locally)), open the interactive documentation in
a browser:

```
http://127.0.0.1:8000/api/docs/
```

Swagger UI renders the schema from `/api/schema/` as an interactive page
where every endpoint listed in the table in [The API](#the-api) is grouped
under `books`. For each endpoint you can see:

- The HTTP method and path, including any path parameters (e.g. `<id>`).
- The expected request body schema (for `POST`/`PUT`/`PATCH`), matching the
  `BookSerializer` fields: `title`, `author`, `isbn`, `published_date`.
- The possible response codes and their payload shape, e.g. `200 OK` with a
  `Book` object for a successful `GET`, `201 Created` for a successful
  `POST`, `204 No Content` for a successful `DELETE`, and `404 Not Found`
  when a book with the given `<id>` does not exist.
- Validation constraints from the serializer, such as `isbn` needing to be
  13 digits and unique.

### Trying out requests

Swagger UI lets you execute real requests against the running server
without leaving the browser:

1. Expand an endpoint (e.g. `POST /api/books/create/`).
2. Click **Try it out**.
3. Fill in the request body (or path parameter, for endpoints like
   `GET /api/books/<id>/`) using the provided example/schema as a guide.
4. Click **Execute**.
5. Swagger UI shows the actual `curl` command sent, the response status
   code, response headers, and the JSON response body returned by the API
   — for example, the created `Book` record with its generated `id`, or a
   `{"detail": "Not found."}` style error for a missing resource.

This is the fastest way to explore the API's behaviour and expected
inputs/outputs without needing a separate REST client such as Postman.
Redoc (`/api/redoc/`) offers the same schema in a read-only, single-page
reference format, which is convenient for browsing but does not support
executing requests.

## Running locally

There are two supported ways to run the project locally: directly with a
Python virtual environment and SQLite (fastest for quick development), or
with Docker Compose and PostgreSQL (closer to production).

### With the virtual environment (SQLite)

This mode uses the bundled `db.sqlite3` file and is controlled by the
`DEVELOPMENT_MODE` setting in `bookcatalog/settings.py`, which switches the
database backend to SQLite when set.

1. **Create and activate a virtual environment** (skip if `.venv` already
   exists):

   ```bash
   python3 -m venv .venv
   source .venv/bin/activate
   ```

2. **Install the dependencies**:

   ```bash
   pip install -r requirements.txt
   ```

3. **Set the environment variable** that tells Django to use SQLite instead
   of PostgreSQL:

   ```bash
   export DEVELOPMENT_MODE=true
   ```

4. **Apply database migrations** to create/update the schema:

   ```bash
   python manage.py migrate
   ```

5. **Start the development server**:

   ```bash
   python manage.py runserver
   ```

Once running, the app is available at:

- API base URL: http://127.0.0.1:8000/api/books/
- Django admin: http://127.0.0.1:8000/admin/
- Swagger UI: http://127.0.0.1:8000/api/docs/

To create an admin user for the Django admin site:

```bash
python manage.py createsuperuser
```

### With Docker Compose (PostgreSQL)

This mode builds the app image from the `Dockerfile` and runs it together
with a PostgreSQL 17 container, as defined in `docker-compose.yml`. It is
the closest local approximation to how the app runs in production.

```bash
docker compose up --build
```

What happens under the hood:

1. Docker Compose builds the app image and starts a `postgres:17` container.
2. The app container's `entrypoint.sh` waits until the database is
   accepting connections.
3. `entrypoint.sh` applies pending migrations automatically
   (`python manage.py migrate`).
4. The Django development server starts and binds to port `8000`.

Once the containers report as healthy/running, the app is available at the
same URLs as above:

- API base URL: http://127.0.0.1:8000/api/books/
- Django admin: http://127.0.0.1:8000/admin/
- Swagger UI: http://127.0.0.1:8000/api/docs/

To stop the stack:

```bash
docker compose down
```

Add `-v` to also remove the PostgreSQL data volume and start from a clean
database on the next run.

## CI/CD pipeline

On pushes and pull requests to `main`, the GitHub Actions workflow
(`.github/workflows/pipeline_steps.yml`) runs three parallel checks using a
shared composite action for setup:

1. **test** — runs the pytest suite
2. **runmigrations** — verifies `python manage.py migrate` applies cleanly
3. **checkmigrations** — `makemigrations --check` ensures no migrations are missing

On `main`, if all checks pass, the pipeline continues:

4. **semantic-release** — analyses conventional commits, tags a new version,
   and updates `CHANGELOG.md`
5. **build-docker-image** — when a new release is published, builds the image
   and pushes it to `ghcr.io/asilvasaraiva/cct-catalog`, tagged with the
   release version

## Kubernetes deployment

The `books-catalog-chart/` Helm chart deploys the app with a Deployment,
Service, Ingress, and ConfigMap. Database migrations run as a Helm
pre-install/pre-upgrade **Job hook** so the schema is up to date before new
pods roll out. The chart pulls its image from
`ghcr.io/asilvasaraiva/cct-catalog` by default (see `image` in
`books-catalog-chart/values.yaml`).

```bash
helm lint ./books-catalog-chart
helm template my-release ./books-catalog-chart
helm install my-release ./books-catalog-chart
```

The database password is read from a Kubernetes Secret (`loadSecretsFrom` in
`values.yaml`), which must be provisioned separately — for example with the
`bitnami/postgresql` chart — before installing this chart.

### Running locally with k3d

[k3d](https://k3d.io/) runs a lightweight k3s Kubernetes cluster inside
Docker, which is a convenient way to try the Helm chart on a local machine
without a cloud cluster. k3s ships with the **Traefik** ingress controller
out of the box, so the chart's `Ingress` resource (path `/api`) works
without installing anything extra. The steps below are the ones actually
used to run this project locally.

1. **Create the cluster**, mapping the load balancer's HTTP/HTTPS ports and
   a range of NodePorts to the host:

   ```bash
   k3d cluster create mycluster \
     --port "8081:80@loadbalancer" \
     --port "8443:443@loadbalancer" \
     --port "30000-30010:30000-30010@server:0"
   ```

2. **Create a pull secret for GHCR**, since the app image is published to a
   GitHub Container Registry repository. `$GH_TOKEN` is a GitHub personal
   access token with at least `read:packages` scope:

   ```bash
   kubectl create secret docker-registry ghcr-token \
     --docker-username=<your_user_name> \
     --docker-password=$GH_TOKEN \
     --docker-server=ghcr.io
   ```

3. **Install PostgreSQL** using the Bitnami OCI chart, with credentials
   matching what the app expects (`DATABASE_USER=books`,
   `DATABASE_NAME=books` in `values.yaml`):

   ```bash
   helm install books-database oci://registry-1.docker.io/bitnamicharts/postgresql --version 18.8.5 \
     --set auth.username=books \
     --set auth.database=books \
     --set auth.password=books
   ```

4. **Install the app chart**, referencing the pull secret created in step 2
   so the cluster can fetch the private GHCR image:

   ```bash
   helm install my-release ./books-catalog-chart \
     --set imagePullSecrets[0].name=ghcr-token
   ```

   The pre-install Job hook runs `python manage.py migrate` against the
   PostgreSQL instance from step 3 before the app Deployment starts.

5. **(Optional) Install Argo CD** to manage the chart via GitOps instead of
   installing it directly with `helm install`:

   ```bash
   helm repo add argo https://argoproj.github.io/argo-helm
   kubectl create namespace argo
   helm install -n argocd argocd argo/argo-cd -f ./argo-helm-values/values.yaml
   ```

   `argo-helm-values/values.yaml` exposes the Argo CD UI under the
   `/argocd` path through the same Ingress/Traefik setup, with
   `server.insecure: true` since TLS is terminated outside the cluster in
   this local setup.

6. **Access the app** through the port mapped in step 1. Since the Ingress
   only matches the `/api` path prefix, use it for the API, Swagger UI,
   admin, etc.:

   ```bash
   curl http://localhost:8081/api/schema/
   ```

   - Swagger UI: http://localhost:8081/api/docs/
   - Redoc: http://localhost:8081/api/redoc/
   - Books endpoint: http://localhost:8081/api/books/

7. **Tear down** the cluster when done:

   ```bash
   k3d cluster delete mycluster
   ```

To pick up a new image after a release, run
`helm upgrade my-release ./books-catalog-chart --set image.tag=<version>`,
or rely on Argo CD to sync the change automatically if it's managing the
release.
